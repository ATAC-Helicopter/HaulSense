# Architecture

The Windows x64 plugin uses the official, vendored SCS Telemetry SDK 1.14 headers. A shared channel registry generates packet fields, subscriptions, availability IDs and JSON values. The PE DLL is freestanding and imports only Winsock and GetTickCount64. It subscribes to changed values and explicitly requests null callbacks when channels become unavailable. Wall-clock sending is capped at 50 Hz, independent of the game's frame rate. Pause and shutdown bypass the rate cap to send neutral state immediately.

A single Linux thread receives fixed-size UDP datagrams (v6 with an exact v5/825-byte prefix adapter and legacy v4/175-byte adapter) and retains the newest valid packet. At most 64 packets are drained per iteration. Effects run at a 20 ms interval; the poll deadline rounds upwards to avoid spinning for fractional milliseconds. Inactive feedback sleeps longer. Effects are computed without controller hardware so diagnostics/UI still work. The hardware-free demo never opens HID/sysfs devices.

The dashboard server binds only to 127.0.0.1. It accepts at most eight clients, bounds requests to 8 KiB and settings bodies to 2 KiB, handles nonblocking partial reads/writes and drops stalled clients after two seconds. A slow dashboard cannot block feedback. No CORS headers are granted, Host is restricted to the local dashboard and writes require a custom same-origin header. Frames are denied and MIME sniffing is disabled. This is a local utility, not a service intended for LAN exposure. Other processes running as the same user can control its local API; it is not an authentication boundary.

Snapshots are serialized on request rather than continuously. The browser polls at 5 Hz while driving and 1 Hz while waiting, stops in hidden tabs, and holds a maximum of 120 chart samples. JSON and DOM inspection are bounded by the static SDK registry and 16 wheels. No network traffic is sent outside loopback by the application. The browser process is separate and is not included in daemon RSS/CPU measurements.

HID transport is identified by the kernel bus type. Player LED paths are matched to the actual selected HID device. Sysfs paths are diagnostic only. Gameplay uses one atomic HID report for all effects, with player-mask bit 5 set to suppress the firmware fade. Unchanged feedback states suppress full effect reports. Player LED validity is set only when the mask changes, so rumble, trigger and RGB updates do not retrigger player commands. The read-only 0x20 feature report supplies hardware info at byte 24, with Bluetooth CRC validation. Known standard generations 4/5 use HUD-only individual turn signals because their player pairs are mirrored; hazards retain symmetric masks. Generations 2/3 are classified independent; unknown revisions and Edge remain unqualified. Directional masks animate inner then the selected pair only on non-mirrored layouts. The center is suppressed during physical directional signals and custom masks are restricted to their selected side; sequential indicators never use per-LED sysfs writes. Feedback caps and gains deliberately avoid permanent RPM or throttle vibration.

Settings updates validate every supplied key before applying any change. Unknown keys, nonfinite/out-of-range numbers, duplicated keys and arbitrary paths are rejected. A replacement config is written beside the existing file and renamed atomically. Existing comments and unrelated keys survive. The old config directory is retained during the product rename.

The legacy adapter marks availability as inferred in the UI and leaves all extended channels absent. It exists to keep a currently running old plugin compatible while the updated DLL is atomically replaced on disk for the next game launch. Legacy pause has only the 500 ms timeout, because the old plugin does not transmit pause events.

The optional GTK HUD polls HTTP in one background thread. GTK updates and rendering remain on the main thread, and a network timeout cannot block window dragging or menus. Both HUDs display GPS travel independently from job destination metadata. Gear, range, cruise and contextual warnings reuse existing channels; no wire ABI changes are needed. See [SDK capabilities](SDK-CAPABILITIES.md).


The v6 packet appends a 38-byte suffix to the unchanged 825-byte v5 ABI: placement availability, three double-precision world coordinates, heading/pitch/roll in SDK turns, and game identity. V5 frames are normalized internally to v6 with no placement; the source version remains visible in snapshots. Placement comes from the SDK dplacement callback with explicit no-value clearing. Coordinates and orientation must be finite and bounded before acceptance.

The navigator embeds same-origin `/navigation.js`, `/scene.js` (MIT Three.js bundle) and `/routing-worker.js`. Detailed imports are limited to 96 MiB with bounded scene arrays, coordinate/reference checks and text-only labels. The canvas fallback and WebGL schematic scene follow dashboard polling without a separate animation loop. A 500-metre index culls objects/prefabs/signs/POIs, road bounding boxes cull lines, and templates, instancing and geometry batching reduce duplication and draw calls. WebGL uses a floating local origin and pixel ratio at most 1.5. The measured trace is bounded to 1,200 points; maps/trip state remain in tab memory. Game mismatch and unavailable placement hide the scene.

Routing runs in a Web Worker with a directed CSR graph and A* search. Road edges retain their curves; prefab links use supplied physical/AI navigation topology. Exact optional GPS UIDs must resolve to known connected directed edges. The independent path is explicitly labelled HaulSense and does not alter game navigation.

A native RouteReader thread polls the optional ETS2LA 96,000-byte local route file every 500 ms. File ownership/type/size and stable reads are checked outside the 50 Hz feedback loop. `/api/route` reports source, availability, freshness and UIDs; freshness requires content change within 2.5 seconds and active non-demo telemetry. Browser route polling runs at most once per second. This ABI has no heartbeat; unchanged stationary routes may be withheld. No provider injection or process-memory access is implemented.

## Standalone release candidate

The standalone Electron main process serves a privileged `haulsense://app` scheme with an explicit resource/API allowlist. API requests are forwarded to the fixed loopback service; renderer code cannot choose filesystem paths, execute Node or communicate through a generic IPC bridge. A persistent partition holds map cache/preferences. A native save dialog handles local JSON downloads. Browser mode remains available. Native/config/world placement data are kept out of remote navigation.

`backgroundThrottling: false` keeps renderer timers/frames live outside focus, while the native service records every accepted UDP frame independently from the UI. Browser hidden tabs still conserve rendering work; background job capture is not tied to browser visibility. The scene and chart remain bounded; no general GPU/FPS guarantee is implied by cached draw timings.

V7 preserves the 863-byte v6 and 825-byte v5 prefixes, adds explicit job state and typed gameplay attributes and remains below the MTU. Gameplay/configuration callbacks force-send a frame; the journal consumes each accepted frame while feedback still uses the newest. V4/v5/v6 normalize into v7 with absent extension values. Native validation checks the extension's masks/booleans/floats.

JobJournal uses a bounded 256-frame queue and a native worker. It aggregates odometer/fuel/speed observations, route segments with gap markers, costs and official delivery attributes. JSON serialization/disk writes stay outside feedback. Checkpoints are atomic every five seconds and on clean shutdown; an abrupt power loss may lose the last checkpoint interval. Completed/cancelled/interrupted reports are separately labelled, retain measured coverage and survive restart. A completion latch avoids creating a second job from the final active frames. Local retention is 50 reports / 10,000 downsampled points per job.

SemaphoreReader samples the optional 40×48-byte ETS2LA feed on a separate 10 Hz thread. File/type/UID/ABI/stable-read and value checks precede publication. Content-change freshness expires after 1.5 seconds and additionally requires active non-demo telemetry. Static map signals are never assigned fabricated phases. See [provider](SIGNAL-PROVIDER.md).
